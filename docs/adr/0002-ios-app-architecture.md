# iOS app: SwiftUI with MVVM, a composition root and a router

## Context and Problem Statement

The iOS app must be easy for agents to extend safely, with a design system that can change at any time, a REST layer, feature flags and full test coverage. Which architecture and project setup gives that?

## Decision Drivers

* Agents add screens by following one checklist
* Tests never need a running backend
* No hand-edited Xcode project files in pull requests

## Considered Options

* SwiftUI + Observation, MVVM, composition root (`AppContainer`), `Router`, protocol-based services, project generated by XcodeGen
* The Composable Architecture (TCA)
* UIKit with coordinators

## Decision Outcome

Chosen option: "SwiftUI + Observation, MVVM, composition root, Router, protocol-based services, XcodeGen", because it uses only Apple frameworks, is the pattern most agents already know, and keeps the project file out of reviews.

### Consequences

* Good, because new features follow one checklist (`apps/ios/.agents/skills/ios-architecture`).
* Good, because `APIClient` has a URLSession client for real backends and a fixture client for tests.
* Good, because feature flags resolve as launch argument or device override, then backend, then default.
* Bad, because XcodeGen must be installed and `make generate` run after pulling.

### Confirmation

CI runs SwiftLint, unit tests with a 70% logic coverage gate, XCUITest UI tests and Maestro end-to-end flows on every pull request that touches `apps/ios`.

## Pros and Cons of the Options

### TCA

* Good, because state changes are very predictable
* Bad, because it is a large dependency with its own learning curve for every contributor and agent

### UIKit with coordinators

* Good, because it is mature
* Bad, because it means more code per screen and no SwiftUI previews
